API Integration

ZapPay API Integration

Accept UPI payments with three API calls. Create a payment order, send your customer to pay, and confirm the result server-side — built for developers shipping fast.

Secure & Reliable Key-based auth with per-account scoping and rate limiting
Easy Integration Simple REST endpoints with copy-paste ready examples
Developer Friendly Real error causes, real fixes — not generic status codes
01

Overview & getting your key

Every ZapPay account has exactly one ZapAPI key — a 32-character secret that authenticates every request you make to ZapAPI. It's the only credential you need.

Where to find it

  1. Log in to your ZapPay dashboard.
  2. Go to Developer Portal → Zap API.
  3. Your key is generated automatically on first visit and shown there — copy it from that screen.

Treat it like a password

  • Never expose it in client-side code that ships to end users — the one exception is the JS widget flow (Section 3), where the key runs from your own page directly against ZapPay's API, not a third party's.
  • Never commit it to a public repository.
  • If it leaks, regenerate it immediately from your dashboard. The old key stops working the instant you do — there's no grace period, so update every integration first if you can.
ZapAPI has two parts: a simple REST API (Section 2) for creating orders and checking their status, and an optional JS widget (Section 3) that wraps the REST API in a ready-made popup checkout.

API reference

Base URL

Base URL 
https://paymentbackend-oga2.vercel.app

Authentication

Every request must include your ZapAPI key, passed one of two ways — the API accepts either:

  • As a field named zap_api in the JSON request body, or
  • As a request header: X-ZapAPI-Key
SituationResponse
Key missing entirely401 — Missing ZapAPI key...

Rate limit

60 requests per 15 minutes, bucketed per ZapAPI key (falls back to your IP address if no key is found on the request).

Create order

POST /api/developer/create-order

Creates a new UPI payment order and returns a payment_url to send your customer to. Requires header Content-Type: application/json.

FieldRequiredTypeNotes
zap_apiYes*string *Only if not using the X-ZapAPI-Key header instead.
amountYesnumber ₹1 to ₹5,000. Must be a plain number — 499, not "₹499" or "4,999".
titleNostring Max 100 chars. Shown as the payment remark. Defaults to "ZapPay Payment".
customer_mobileNostring 10 digits, optionally prefixed with 91 / +91 / a leading 0 — no spaces or dashes. Prefills the customer's UPI app.
redirect_urlNostring Where the customer lands after paying. ZapPay appends ?zp_order=<id>&zp_result=success|failed. Ignored if useEmbedded: true.
useEmbeddedNoboolean Set true for the JS widget / in-app popup flow. No server redirect URL is generated in that case.
#1 real cause of "Validation failed": sending amount as a formatted price string instead of a clean number. Strip currency symbols and commas — Number(String(price).replace(/[^0-9.]/g,'')) — before calling create-order. See the full Error Reference below for every failure mode.

Get order status

GET /api/developer/order-status/:orderId

Returns the current status of an order. No request body — orderId is a path parameter (the order_id returned by create-order). Requires the X-ZapAPI-Key header.

Orders are scoped to the calling key's owner — you can never fetch another merchant's order, even by guessing its ID.

200 — status fetched
{
  "success": true,
  "message": "Status fetched",
  "data": {
    "order_id": "ZP1782...ABCD",
    "status": "success",
    "amount": 100
  }
}

status is always exactly one of: "pending" · "success" · "failed".

The single most important rule in this document: a customer landing back on your redirect_url, or a client-side JS callback firing, is never proof of payment on its own. Both can be spoofed, retried, or interrupted. Always call order-status from your server and check status === "success" before marking anything as paid.
03

Integration guide

Pick your stack. Each example is complete and runnable — swap in your ZapAPI key and you're live.

Drop in the widget script, set your callbacks, and call createOrder. The widget handles opening the payment popup and polling for you.

index.html
<script src="https://zetpay.online/zappay-pay.js"></script>

<button onclick="payNow()">Pay ₹100</button>

<script>
  ZapPay.setCallbacks({
    onSuccess: (order) => {
      // order = { order_id, amount }
      console.log('Payment successful:', order.order_id);
      // TODO: confirm server-side via order-status before fulfilling
    },
    onFailed: (order) => {
      // order = { order_id, amount } OR { error } on network/validation failure
      console.log('Payment failed:', order);
    },
    onTimeout: (order) => {
      // order = { order_id, amount }
      // Fires after ~2 minutes of polling, or if the popup was closed
      console.log('Payment timed out:', order);
    }
  });

  function payNow() {
    ZapPay.createOrder({
      zap_api: 'YOUR_ZAPAPI_KEY',
      amount: 100,
      title: 'Order #123',        // optional
      customer_mobile: '9999999999' // optional
    });
  }
</script>
Internally, createOrder always sends useEmbedded: true and opens payment_url in a 430×700 popup (falling back to a same-tab redirect if the popup is blocked). It then polls order-status every 2.5s, up to 48 times (~2 minutes), and fires your callbacks automatically.
Widget fails silently on bad input. On a missing zap_api or amount, it only logs console.error — no callback fires. Verify typeof ZapPay !== 'undefined' before calling it, and test the real click end-to-end.

Two scripts: one to create the order server-side and redirect the customer, and one to handle their return and confirm payment before trusting it.

A redirect back to your site is a fresh page load, not a resumed session. Any client-side state your checkout page had (a filled-in form, a cart, scroll position) is gone the moment the customer's browser leaves for payment_url — redirect_url only carries a URL, not JavaScript memory. If you need something from before checkout to still be there afterwards, save it (server-side session, or a client-side store keyed by an id you attach to redirect_url yourself) before redirecting, and restore it on return using that id. The example below does this with a PHP session.
create-order.php
<?php
session_start();

// Save whatever this page knows before the customer leaves for checkout —
// a redirect is a full page navigation, so nothing in this script's memory
// (or a plain HTML form's values) survives it on its own. A PHP session
// does, because it's tied to the customer's browser via a cookie, not to
// this one request.
$_SESSION['customer_name']  = $_POST['name']  ?? '';
$_SESSION['customer_phone'] = $_POST['phone'] ?? '';

$ch = curl_init('https://paymentbackend-oga2.vercel.app/api/developer/create-order');
curl_setopt($ch, CURLOPT_POST, true);
curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
curl_setopt($ch, CURLOPT_HTTPHEADER, ['Content-Type: application/json']);
curl_setopt($ch, CURLOPT_POSTFIELDS, json_encode([
    'zap_api'      => 'YOUR_ZAPAPI_KEY',
    'amount'       => 100,
    'title'        => 'Order #123',
    'redirect_url' => 'https://yourstore.com/payment-return.php'
]));

$response = curl_exec($ch);
curl_close($ch);

$result = json_decode($response, true);

if ($result['success']) {
    // Send the customer to complete payment
    header('Location: ' . $result['data']['payment_url']);
    exit;
} else {
    // Handle error — see Error Reference below for all possible messages
    echo 'Could not start payment: ' . $result['message'];
}
payment-return.php
<?php
session_start();
// $_GET['zp_order'] and $_GET['zp_result'] are appended by ZapPay automatically.
// IMPORTANT: zp_result in the query string must NEVER be trusted alone —
// it can be spoofed. Always confirm via order-status server-side.

$orderId = $_GET['zp_order'] ?? null;

if (!$orderId) {
    die('Missing order id.');
}

$ch = curl_init("https://paymentbackend-oga2.vercel.app/api/developer/order-status/{$orderId}");
curl_setopt($ch, CURLOPT_RETURNTRANSFER, true);
curl_setopt($ch, CURLOPT_HTTPHEADER, [
    'X-ZapAPI-Key: YOUR_ZAPAPI_KEY'
]);

$response = curl_exec($ch);
curl_close($ch);

$result = json_decode($response, true);

// Read back what create-order.php saved before the customer left — this
// is what makes the page feel like it "remembered" them, instead of
// showing a blank confirmation with no name/phone reference.
$customerName  = $_SESSION['customer_name']  ?? null;
$customerPhone = $_SESSION['customer_phone'] ?? null;

if ($result['success'] && $result['data']['status'] === 'success') {
    // Verified server-side — safe to fulfill the order now
    echo 'Payment confirmed for order ' . $result['data']['order_id'];
    if ($customerName) {
        echo ' — thanks, ' . htmlspecialchars($customerName) . '!';
    }
    // This session's job is done — clear it so a later visit doesn't
    // show stale customer details.
    unset($_SESSION['customer_name'], $_SESSION['customer_phone']);
} elseif ($result['success'] && $result['data']['status'] === 'pending') {
    echo 'Payment still pending — check again shortly.';
} else {
    echo 'Payment failed or order not found.';
}

OkHttp example: create the order, open payment_url in a Chrome Custom Tab, then poll order-status until it resolves.

ZapPayClient.java
OkHttpClient client = new OkHttpClient();
String ZAP_API_KEY = "YOUR_ZAPAPI_KEY";
String BASE_URL = "https://paymentbackend-oga2.vercel.app";

// 1. Create the order
public void createOrder(double amount, String title, OrderCallback callback) {
    JSONObject body = new JSONObject();
    try {
        body.put("zap_api", ZAP_API_KEY);
        body.put("amount", amount);
        body.put("title", title);
        body.put("useEmbedded", true);
    } catch (JSONException e) {
        callback.onError(e.getMessage());
        return;
    }

    RequestBody requestBody = RequestBody.create(
        body.toString(), MediaType.parse("application/json"));

    Request request = new Request.Builder()
        .url(BASE_URL + "/api/developer/create-order")
        .post(requestBody)
        .build();

    client.newCall(request).enqueue(new Callback() {
        @Override
        public void onFailure(Call call, IOException e) {
            callback.onError(e.getMessage());
        }

        @Override
        public void onResponse(Call call, Response response) throws IOException {
            try {
                JSONObject json = new JSONObject(response.body().string());
                if (json.getBoolean("success")) {
                    JSONObject data = json.getJSONObject("data");
                    String orderId = data.getString("order_id");
                    String paymentUrl = data.getString("payment_url");

                    // 2. Open payment_url in a Chrome Custom Tab
                    openCustomTab(paymentUrl);

                    // 3. Start polling for the result
                    pollOrderStatus(orderId, callback);
                } else {
                    callback.onError(json.getString("message"));
                }
            } catch (JSONException e) {
                callback.onError(e.getMessage());
            }
        }
    });
}

void openCustomTab(String url) {
    CustomTabsIntent intent = new CustomTabsIntent.Builder().build();
    intent.launchUrl(context, Uri.parse(url));
}

// Poll order-status every ~2.5s until it resolves
Handler handler = new Handler(Looper.getMainLooper());

public void pollOrderStatus(String orderId, OrderCallback callback) {
    Request request = new Request.Builder()
        .url(BASE_URL + "/api/developer/order-status/" + orderId)
        .header("X-ZapAPI-Key", ZAP_API_KEY)
        .get()
        .build();

    client.newCall(request).enqueue(new Callback() {
        @Override
        public void onFailure(Call call, IOException e) {
            callback.onError(e.getMessage());
        }

        @Override
        public void onResponse(Call call, Response response) throws IOException {
            try {
                JSONObject json = new JSONObject(response.body().string());
                if (json.getBoolean("success")) {
                    String status = json.getJSONObject("data").getString("status");

                    if (status.equals("success")) {
                        callback.onSuccess(json.getJSONObject("data"));
                    } else if (status.equals("failed")) {
                        callback.onFailed(json.getJSONObject("data"));
                    } else {
                        // still "pending" — poll again in 2.5s
                        handler.postDelayed(() ->
                            pollOrderStatus(orderId, callback), 2500);
                    }
                } else {
                    callback.onError(json.getString("message"));
                }
            } catch (JSONException e) {
                callback.onError(e.getMessage());
            }
        }
    });
}

public interface OrderCallback {
    void onSuccess(JSONObject data);
    void onFailed(JSONObject data);
    void onError(String message);
}
Only mark the purchase as fulfilled inside onSuccess, once pollOrderStatus has confirmed status == "success" from your own server-to-server call — never on the basis of the Custom Tab simply closing.

Coroutine-based OkHttp example: create the order, open payment_url in a Chrome Custom Tab, then suspend-poll order-status until it resolves.

ZapPayClient.kt
class ZapPayClient(private val context: Context) {
    private val client = OkHttpClient()
    private val zapApiKey = "YOUR_ZAPAPI_KEY"
    private val baseUrl = "https://paymentbackend-oga2.vercel.app"
    private val JSON = "application/json; charset=utf-8".toMediaType()

    data class OrderResult(val orderId: String, val status: String, val amount: Double)

    suspend fun createOrder(amount: Double, title: String): OrderResult = withContext(Dispatchers.IO) {
        val body = JSONObject().apply {
            put("zap_api", zapApiKey)
            put("amount", amount)
            put("title", title)
            put("useEmbedded", true)
        }
        val request = Request.Builder()
            .url("$baseUrl/api/developer/create-order")
            .post(body.toString().toRequestBody(JSON))
            .build()

        client.newCall(request).execute().use { response ->
            val json = JSONObject(response.body!!.string())
            if (!json.getBoolean("success")) throw Exception(json.getString("message"))
            val data = json.getJSONObject("data")
            openCustomTab(data.getString("payment_url"))
            pollOrderStatus(data.getString("order_id"))
        }
    }

    private fun openCustomTab(url: String) {
        CustomTabsIntent.Builder().build().launchUrl(context, Uri.parse(url))
    }

    suspend fun pollOrderStatus(orderId: String): OrderResult = withContext(Dispatchers.IO) {
        while (true) {
            val request = Request.Builder()
                .url("$baseUrl/api/developer/order-status/$orderId")
                .header("X-ZapAPI-Key", zapApiKey)
                .get().build()

            client.newCall(request).execute().use { response ->
                val json = JSONObject(response.body!!.string())
                if (!json.getBoolean("success")) throw Exception(json.getString("message"))
                val data = json.getJSONObject("data")
                val status = data.getString("status")
                if (status == "success" || status == "failed") {
                    return@withContext OrderResult(orderId, status, data.getDouble("amount"))
                }
            }
            delay(2500)
        }
        @Suppress("UNREACHABLE_CODE")
        throw IllegalStateException()
    }
}

// Usage (from a coroutine scope, e.g. viewModelScope):
// val result = zapPayClient.createOrder(100.0, "Order #123")
// if (result.status == "success") { /* fulfill */ }
Only fulfill once pollOrderStatus itself returns status == "success" — that's the actual server-to-server confirmation, not just the Custom Tab closing.

Express example: one route creates the order server-side and redirects the customer, another handles their return and confirms payment before trusting it.

routes/checkout.js
const express = require('express');
const router = express.Router();

const ZAP_API_KEY = process.env.ZAP_API_KEY;
const BASE_URL = 'https://paymentbackend-oga2.vercel.app';

router.post('/create-order', async (req, res) => {
    const response = await fetch(`${BASE_URL}/api/developer/create-order`, {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({
            zap_api: ZAP_API_KEY,
            amount: req.body.amount,
            title: req.body.title || 'ZapPay Payment',
            redirect_url: 'https://yourstore.com/payment-return'
        })
    });
    const result = await response.json();

    if (!result.success) {
        return res.status(400).json({ error: result.message });
    }
    res.redirect(result.data.payment_url);
});

// redirect_url lands here: zp_order and zp_result are appended by ZapPay.
// zp_result in the query string must NEVER be trusted alone — it can be
// spoofed. Always confirm via order-status from this server.
router.get('/payment-return', async (req, res) => {
    const orderId = req.query.zp_order;
    if (!orderId) return res.status(400).send('Missing order id.');

    const response = await fetch(`${BASE_URL}/api/developer/order-status/${orderId}`, {
        headers: { 'X-ZapAPI-Key': ZAP_API_KEY }
    });
    const result = await response.json();

    if (result.success && result.data.status === 'success') {
        res.send(`Payment confirmed for order ${result.data.order_id}`);
    } else if (result.success && result.data.status === 'pending') {
        res.send('Payment still pending — check again shortly.');
    } else {
        res.status(400).send('Payment failed or order not found.');
    }
});

module.exports = router;
Never branch fulfillment logic on req.query.zp_result alone. The only trustworthy signal is a server-to-server order-status call returning status === "success".

The ZapPay widget script, wired up as plain JS for projects without inline <script> tags — a bundled site, a CMS custom-JS block, etc. Same mechanism as the HTML/JS tab.

checkout.js
// <script src="https://zetpay.online/zappay-pay.js"><\/script> must already be on the page

ZapPay.setCallbacks({
    onSuccess: function (order) {
        console.log('Payment successful:', order.order_id);
        // UI signal only — confirm server-side via order-status before fulfilling.
        fetch('/api/confirm-order?order_id=' + encodeURIComponent(order.order_id))
            .then(r => r.json())
            .then(data => {
                if (data.confirmed) {
                    document.getElementById('checkout-status').textContent = 'Payment confirmed!';
                }
            });
    },
    onFailed: function (order) {
        document.getElementById('checkout-status').textContent = 'Payment failed.';
    },
    onTimeout: function (order) {
        document.getElementById('checkout-status').textContent = 'Payment timed out.';
    }
});

document.getElementById('pay-button').addEventListener('click', function () {
    ZapPay.createOrder({
        zap_api: 'YOUR_ZAPAPI_KEY', // for a real site, proxy this through your own
                                     // server instead of shipping the key client-side

        title: 'Order #123',
        customer_mobile: document.getElementById('phone-input').value
    });
});

// /api/confirm-order on YOUR server, called above, should itself call:
// GET https://paymentbackend-oga2.vercel.app/api/developer/order-status/:orderId
// with header X-ZapAPI-Key: YOUR_ZAPAPI_KEY, and only report confirmed: true

Even though onSuccess fired client-side, treat that as a UI signal only. The /api/confirm-order round trip above (a server-side order-status check) is what actually gates fulfillment — never ship goods based on onSuccess alone.

Flask + requests example: one route creates the order and redirects the customer, another handles their return and confirms payment independently before trusting it.

app.py
import os
import requests
from flask import Flask, request, redirect, jsonify

app = Flask(__name__)

ZAP_API_KEY = os.environ['ZAP_API_KEY']
BASE_URL = 'https://paymentbackend-oga2.vercel.app'

@app.route('/create-order', methods=['POST'])
def create_order():
    resp = requests.post(f'{BASE_URL}/api/developer/create-order', json={
        'zap_api': ZAP_API_KEY,
        'amount': request.json['amount'],
        'title': request.json.get('title', 'ZapPay Payment'),
        'redirect_url': 'https://yourstore.com/payment-return'
    })
    result = resp.json()

    if not result['success']:
        return jsonify({'error': result['message']}), 400
    return redirect(result['data']['payment_url'])

# redirect_url lands here: zp_order and zp_result are appended by ZapPay.
# zp_result in the query string must NEVER be trusted alone — it can be
# spoofed. Always confirm via order-status from this server.
@app.route('/payment-return')
def payment_return():
    order_id = request.args.get('zp_order')
    if not order_id:
        return 'Missing order id.', 400

    resp = requests.get(
        f'{BASE_URL}/api/developer/order-status/{order_id}',
        headers={'X-ZapAPI-Key': ZAP_API_KEY}
    )
    result = resp.json()

    if result['success'] and result['data']['status'] == 'success':
        return f"Payment confirmed for order {result['data']['order_id']}"
    elif result['success'] and result['data']['status'] == 'pending':
        return 'Payment still pending — check again shortly.'
    else:
        return 'Payment failed or order not found.', 400

if __name__ == '__main__':
    app.run(port=5000)
Never branch fulfillment logic on request.args.get('zp_result') alone. The only trustworthy signal is a server-to-server order-status call returning status == "success".

Error reference

Every error this API can return — what it means, why it happens, and exactly how to fix it

Tap any error to expand it. Each one lists the real, verified cause from the API's own validation and auth code — not a generic guess.

401
Missing ZapAPI key"Missing ZapAPI key..."
{ "success": false, "message": "Missing ZapAPI key. Pass it as \"zap_api\" in the request body or an \"X-ZapAPI-Key\" header." }
Why it happens

Neither a zap_api field in the JSON body nor an X-ZapAPI-Key header was found on the request. The API checks both locations and only fails if both are empty.

How to fix

Add your key to the request. Easiest for server calls: send it as the X-ZapAPI-Key header. For the JS widget, pass zap_api inside the object you give to createOrder(). Double-check the key variable isn't empty/undefined at the point you send it — this is often a config or .env loading issue, not a typo in the field name.

401
Invalid ZapAPI key"Invalid ZapAPI key"
{ "success": false, "message": "Invalid ZapAPI key" }
Why it happens

A key was sent, but it doesn't resolve to any account. The three most common causes: you regenerated your key at some point and an old copy is still hardcoded somewhere; you copy-pasted the key with a missing character or extra space; or you're accidentally using a key from a different environment (e.g. a teammate's).

How to fix

Go to Developer Portal → Zap API in your dashboard and copy the key shown there fresh — don't retype it by hand. If you regenerated your key recently, make sure every place that uses it (server env vars, JS widget calls, mobile app config) was updated — regenerating invalidates the old one instantly with no grace period.

403
Account suspended"This account has been suspended."
{ "success": false, "message": "This account has been suspended.", "banned": true }
Why it happens

Your key is valid and resolves correctly, but the ZapPay account that owns it has been suspended. This check runs on every single ZapAPI request — a suspended account can't create orders or check statuses even with a perfectly valid key.

How to fix

This isn't something you can fix in code. Contact ZetPay Support to find out why the account was suspended and resolve it — the API will keep returning this on every request until the suspension is lifted on ZapPay's side.

400
Validation failed"Validation failed"
{ "success": false, "message": "Validation failed", "errors": [ { "msg": "Amount must be between ₹1 and ₹5,000", "...": "..." } ] }
Why it happens

The request reached create-order fine, but one of its fields failed validation. In order of real-world frequency:

1. amount sent as a formatted string — e.g. "₹499" or "1,999" instead of a plain number like 499. The API requires a clean float between 1 and 5000.

2. customer_mobile has spaces, dashes, or brackets — a value typed by a real user like "+91 98765 43210" fails; it must be exactly 10 digits, optionally preceded by 91/+91/a leading 0, with nothing else.

3. title is over 100 characters.

How to fix

Sanitize before sending: Number(String(price).replace(/[^0-9.]/g,'')) for amount, and strip all non-digits from any user-typed phone number (or omit customer_mobile entirely — it's optional). Log the errors array in dev to see exactly which field failed rather than guessing.

400
Wallet full"Your ZapPay wallet is full..."
{ "success": false, "message": "Your ZapPay wallet is full. Upgrade your plan or withdraw first." }
Why it happens

Your current wallet balance plus this order's amount would exceed your plan's wallet limit. This only applies in Live Mode — the check is intentionally skipped for Test Mode orders so testing your integration is never blocked by wallet headroom.

How to fix

From your dashboard, either withdraw funds to bring your balance down, or upgrade to a plan with a higher wallet limit. This is an account-level limit, not something a request parameter can override.

404
Order not found"Order not found"
{ "success": false, "message": "Order not found" }
Why it happens

Returned by order-status when either the orderId in the URL doesn't exist at all, or it exists but belongs to a different ZapPay account than the one your key resolves to. Both cases return the identical message on purpose, so a caller can never learn whether an order ID belongs to someone else.

How to fix

Confirm you're passing the exact order_id string returned by create-order, unmodified. If you're polling with a hardcoded key during testing, make sure it's the same key that created the order — a mismatched key on a real order looks identical to a typo'd order ID.

429
Rate limited"Too many API requests..."
{ "success": false, "message": "Too many API requests. Please try again later." }
Why it happens

You've made more than 60 requests in a 15-minute window on this key (or IP, if no key was found). This bucket is shared across both create-order and order-status calls made with the same key. A common accidental trigger: polling order-status faster than every 2–3 seconds, or a retry loop with no backoff.

How to fix

If you're polling manually, slow down to at least every 2.5 seconds — this is exactly the interval the official JS widget uses internally, and it never hits this limit for a single order. Add exponential backoff to any retry logic. Wait for the 15-minute window to reset; there's no way to lift it early.

503
Maintenance mode"Payment system is under maintenance."
{ "success": false, "message": "Payment system is under maintenance." }
Why it happens

ZapPay itself has temporarily paused new order creation platform-wide. This is unrelated to your account, key, or request — it only ever appears on create-order in Live Mode, never on order-status, and never on Test Mode orders.

How to fix

Nothing to change in your code. Retry after a short delay — this is expected to be temporary. If it persists for an extended period, check ZapPay's status page or contact support.

JS
Widget: nothing happens on clickconsole: "zap_api key is required" / "amount is required"
Why it happens

This is not an API error — it never reaches the network. The zappay-pay.js widget checks zap_api and amount are present before making any request, and if either is missing, it only logs to the console and returns silently. No callback fires, nothing visibly happens on the page.

How to fix

Open the browser console when testing — this failure mode is invisible in the UI by design. Confirm the object passed to ZapPay.createOrder({...}) actually contains non-empty zap_api and amount values at the moment it's called, not just in the code that looks correct on paper.

JS
Widget: "Failed to fetch"onFailed: { error: 'network_error' }
Why it happens

The widget's backend URL is hardcoded inside zappay-pay.js — it never depends on which domain served the script file, so this is not a hosting or CORS problem on your end. It almost always means the page loaded an old or incomplete cached copy of the script.

How to fix

Re-copy the <script src="https://zetpay.online/zappay-pay.js"> tag fresh from Section 3 and hard-refresh the page (clear cache). If you're loading the script from your own CDN/proxy, confirm it's actually serving the latest file content, not a stale cached copy.

05

Test Mode & Live Mode

Every ZapPay account has a Gateway Mode, switchable any time from Developer Portal → Zap API. It applies account-wide — both create-order and every payment link — and defaults to Live, so nothing changes for an existing integration until you switch it yourself.

  • Live Mode — real UPI checkout, real money, real wallet credit.
  • Test Mode — create-order returns a payment_url pointing at ZapPay's own simulator instead of a real UPI checkout. Opening it shows a "Test Action" button with three outcomes: Successfully, Failed, and Cancelled. Your wallet is never credited — no money moves.

The important part: nothing else changes shape. order-status returns the exact same pending / success / failed values either way, so whatever polling logic you write works against Test Mode without any special-casing.

Leaving Test Mode on is the single most common reason a "live" integration silently stops accepting real payments. If customers report they can't pay, check Developer Portal → Zap API first.
06

Best practices & security

  • Never trust a redirect or client callback alone. Always call order-status from your server and check status === "success" before fulfilling an order.
  • Keep your ZapAPI key server-side wherever possible. The JS widget is the one exception — there the key is used from your own page directly against ZapPay's API.
  • One checkout at a time. Don't call create-order again for the same purchase while a previous order is still pending — check its status first.
  • Regenerate your key immediately if you suspect it has leaked. The old key is invalidated instantly, with no grace period.
  • Respect the amount limit. ₹1 to ₹5,000 — validate client-side too, before you ever hit the API.
  • Respect the rate limit. 60 requests / 15 minutes per key. Poll no more often than every 2–3 seconds.
